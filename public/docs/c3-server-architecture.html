CHAPTER 01

Executive decision

Build an authoritative Rust server with a shared Rust simulation core compiled to WebAssembly for browser prediction. Use Rapier 3D as the leading physics candidate. Keep rendering assets completely separate from collision assets.

This is an architecture proposal and decision document, not an implemented or benchmarked server. “AAA strength” is a quality objective: reliable simulation, secure authority, measurable latency, controlled memory, robust operations and evidence from production-like testing. No player capacity or performance is certified here.

Recommended baseline: Rust + Rapier + browser WASM + Docker. Approve after a native/WASM determinism experiment and a representative physics benchmark, not from language reputation.
CHAPTER 02

Architecture overview

Each room has one authoritative owner. Networking tasks authenticate and decode bounded messages; they do not mutate physics directly. A room tick consumes an ordered command queue, advances simulation, records events and produces immutable snapshot data. Snapshot encoding and socket delivery happen outside the critical simulation step.

Account storage, orchestration and telemetry are services around the simulation. A database is never queried synchronously inside the physics tick. Initially deploy a small number of isolated rooms per process; expand only after CPU and memory profiles show safe density.

CHAPTER 04

The server needs colliders, not artwork

Your intuition is correct: the server does not need the actual display model. It needs collision geometry and physical state. An “outline” is closer to a collision volume or surface than a visual outline. A bounding box alone is useful for broad-phase filtering, but usually cannot represent doorways, stairs or accurate contacts.

ObjectBrowser displayServer collision representation
PlayerSkinned mesh, clothing, textures, animation graphCapsule controller; optional gameplay hit volumes
BuildingDetailed facade, interior decorations, windowsWall/floor boxes, doorway gaps, simplified static mesh where needed
DoorDecorated mesh and animationBox with a server-owned hinge/kinematic transform
VehicleHigh-detail body, wheels, lightsCompound convex chassis; wheels via selected raycast/contact model
TerrainRendered terrain tiles and material layersMatching collision heightfield or simplified static mesh
Trees / plantsLeaves, wind animation, bark texturesTrunk capsule if gameplay requires; most foliage has no collider
DebrisVisual particles and fragment meshesOnly a bounded subset of gameplay fragments; rest client cosmetic

Do not replace an enterable house with one convex hull: that fills the interior and seals entrances. Build it from wall sections and floors, or a simplified static concave mesh. Moving objects generally use primitive or compound convex shapes. Rapier discourages triangle-mesh colliders on dynamic rigid bodies. [S2]

CHAPTER 05

Asset cooking and collision contracts

Cooking happens offline or during an authorized content build, not repeatedly inside a room. Prefer authored primitives; next use validated convex hulls or offline convex decomposition; use simplified triangle meshes for static concave structures. Store collider-local transforms, units in metres, collision groups, physical materials, mass policy, asset revision and content hash. Render materials and physical materials are separate concepts.

Reject non-finite coordinates, degenerate geometry, extreme scale, excessive triangle counts and too many hulls. Validate doorway clearance, floor continuity and stairs with capsule sweeps. Collision detail must preserve playable dimensions even when visual LOD changes. Never use render LOD to silently alter authoritative collision geometry.

In procedural cities, the same approved building recipe produces visual and collision packages. Server-approved edits are assigned an activation tick and asset revision. Clients acknowledge collision readiness before entering affected regions; otherwise delay entry or use a safe loading boundary.

CHAPTER 06

Memory model and streaming

Collision-only simulation removes textures, vertex shading attributes, animation rigs and GPU buffers from server memory. It does not eliminate geometry, collision acceleration structures, contact caches, broad-phase data, joints or rollback history. Sleeping bodies reduce work but still occupy memory.

Memory categoryControl strategy
Shape geometryCache immutable shared shapes by asset hash; multiple colliders reference the same shape. Rapier SharedShape supports shared ownership. [S3]
InstancesPer-instance transform, body state, material overrides and stable entity mapping still cost memory.
Static sceneLoad authoritative collision cells around active gameplay plus an interaction margin; use reference counts and unload hysteresis.
Contacts / broad phaseProfile dense stacks, crowded doors and overlapping sensors; geometry count alone is misleading.
HistoryBound prediction, lag-compensation and rollback windows separately; retain only required data.
Network queuesCap outbound backlog, snapshot size and per-peer input history; disconnect chronically slow consumers.
Asset decodingRelease temporary cooking/decoding buffers; limit concurrent loads and avoid duplicate geometry copies.

Example payload arithmetic only: a mesh with V float32 positions and T uint32 triangles stores approximately 12V + 12T bytes before acceleration structures and allocator overhead. A 10,000-vertex / 20,000-triangle collision mesh therefore has about 360,000 bytes of raw arrays. This is not a measured total engine footprint. A primitive is much smaller, but the enclosing body and collider still have overhead.

Measure RSS, peak load memory, shape-cache size, body/collider counts, contacts, retained history and queue bytes. Enforce per-room caps rather than assuming all objects have equal cost. Avoid full-engine snapshots every tick until profiling proves their memory and replay cost acceptable.

CHAPTER 07

What “same physics” actually means

Both builds should use the same Rust crate for input processing, movement controller, collision queries, physical rules and Rapier integration. Compile that crate natively for the server and to wasm32 for the browser, with a small binding API. Render and network frameworks live outside it.

Rapier supports cross-platform deterministic simulation when its stated conditions are satisfied: matching initial structures and insertion/removal ordering, enhanced-determinism, compatible floating-point targets and deterministic initialization math. [S1] This is conditional engine capability, not automatic end-to-end multiplayer determinism.

Must matchRequired discipline
Simulation stepFixed dt, gravity, solver/CCD settings, controller constants and tick order.
BuildPinned engine/toolchain/features; test native x86, ARM and supported browser WASM targets.
SceneSame collision geometry bytes, transforms, physical properties and activation ticks.
OrderingStable entity IDs; canonical spawn/despawn, commands and event order; no unordered hash iteration driving mutation.
Math / randomShared deterministic math paths and seeded PRNG; no Date.now, browser trig or wall-clock dt inside simulation.
ExecutionDo not assume parallel feature flags or SIMD configurations preserve parity; use the pinned engine version’s documented compatible configuration.
SerializationCanonical gameplay state representation; do not hash memory addresses, uninitialized padding or ephemeral engine handles.
A client simulating only its local neighborhood does not have the same complete world as the server. Matching engines reduces divergence; it does not remove the need for authoritative reconciliation.

Keep server snapshots even if replay tests are bit-identical. Input arrival differs, remote actions may be unknown, relevant objects enter the client world late and collision streaming changes available state. Full deterministic lockstep is a different architecture and is not the baseline.

CHAPTER 08

Tick pipeline and time

  1. Read validated commands eligible for the current tick; apply stable ordering.
  2. Apply scheduled spawns, despawns and collision asset activations.
  3. Update player controllers and authoritative kinematic objects.
  4. Advance Rapier by one fixed timestep.
  5. Process bounded contact/gameplay events in canonical order.
  6. Commit gameplay changes, record selected history and extract snapshots.
  7. Publish metrics and enqueue immutable output without blocking the tick.

Start with a proposed 60 Hz simulation and 20 Hz snapshot cadence; these are tuning hypotheses. A 60 Hz tick has a 16.67 ms wall-clock interval. Aim for p99 simulation work below half that interval at the agreed room load so encoding, scheduling and bursts have headroom. Measure on declared hardware.

A monotonic server clock schedules ticks. Client clock synchronization estimates server tick and drift; it does not grant authority over time. Cap catch-up work. Under overload, preserve simulation dt, shed admission and disconnect excess load before allowing unlimited queues. Never solve overload by silently increasing physics dt.

CHAPTER 09

Prediction and reconciliation

Each input contains a sequence, intended tick, bounded axes/buttons and optional look orientation. The server accepts a bounded lead/lag window, caps processing rate and acknowledges the last applied input. Render rate never determines movement speed.

On an authoritative update, compare against the predicted state for that tick. Restore authoritative movement state, then replay pending inputs using the shared controller. Immediately correct the simulation collider; apply a short-decaying visual offset to hide small adjustments. Teleports and large invalid errors reset smoothing and histories.

Position and velocity alone may be insufficient for faithful replay. Capture grounded mode, jump timers, platform attachment and any controller state affecting future motion. For interacting dynamic bodies, contacts and solver history complicate rollback. Begin with player-only prediction and interpolated server-owned props. Add predicted interactions only after a tested restore/replay contract covers the relevant body island.

CHAPTER 10

Remote interpolation and recovery

Buffer snapshots by server tick and render remote entities behind estimated server time. Interpolate positions and use quaternion interpolation for orientation. An initial 100 ms buffer is an experiment, not a fixed recommendation; adapt within bounds to measured jitter and snapshot cadence.

If a snapshot is late, permit only short bounded extrapolation, then freeze or degrade gracefully. Never extrapolate forever. Spawn/despawn and teleports are discrete events, not interpolation curves. Interpolation buffers and physical prediction are separate stores.

On reconnect, authenticate again, obtain a complete baseline and clear obsolete input/snapshot history. A new session epoch prevents stale packets from an old connection mutating state. Delta snapshots identify their baseline and never assume a client received an unavailable base.

A controller can be kinematic rather than a freely tumbling rigid body. Define pushing, stepping, slopes, ground snapping and platform motion as game rules. Server-authoritative does not mean every object must be physically simulated.

Use collision groups to skip impossible interactions, selective CCD rather than blanket activation, and explicit mass/inertia for proxies where collider volume would give misleading values. Bound joints, debris and high-energy interactions. Choose stability and believable outcomes before adding costly detail.

CHAPTER 12

Animation synchronization

Synchronize semantic state: locomotion mode, velocity, grounded flag, stance, action ID, action start tick, playback variant and cancellation. Clients derive blends and play visual poses. Do not stream every bone for ordinary characters.

The server determines when an attack, jump or interaction has gameplay effect. The animation can visually anticipate an action, but hits are awarded by server rules. Late joiners reconstruct action phase from the server timeline; event IDs suppress duplicate effects.

For root motion, export a versioned movement curve consumed by the shared core or use controller-driven movement with in-place animation. Do not make authoritative distance depend on browser animation frames. Gameplay hit volumes use compact capsules/boxes or validated pose samples rather than loading full render skeletons.

Foot IK, cloth, facial animation, camera shake and cosmetic particles stay client-side. If bone-driven hitboxes are required later, document pose sampling, temporal alignment and lag-compensation policy before implementation.

CHAPTER 13

Protocol and browser transport

Start with TLS WebSockets for broad browser compatibility and operational simplicity. Reliable ordered delivery can cause head-of-line delay when stale state is queued. Design transport-independent messages and bounded queues so a later WebTransport experiment can offer reliable control streams plus datagrams for replaceable state where browser and infrastructure support it.

MessageMinimum fields
Hello / welcomeProtocol version, simulation build ID, asset schema, room/session epoch, server tick.
Input batchSequence, tick, quantized axes, button mask, look; bounded batch count.
SnapshotServer tick, baseline ID, acknowledged input, entity IDs/revisions, transforms, velocities, gameplay flags.
Reliable eventEvent ID, entity ID, action type, authoritative tick, bounded payload.
World patchRevision, collision asset hashes, activation tick, changed entity records.
ResyncReason, last known baseline, requested complete state; server rate limit.

Use a versioned binary schema, length limits and explicit validation. Quantization reduces bandwidth but changes reconstructed values; native/WASM tests must include the exact quantized input path. Quantize snapshots as a deliberate error budget, not arbitrary rounding. Never derive contact outcomes from render-interpolated transforms.

Illustrative bandwidth: 40 entities × 48 encoded bytes × 20 snapshots/s = 38,400 bytes/s per client before framing, events and retransmissions. This is arithmetic, not a measured protocol size. Interest management, sleeping-state suppression and delta encoding reduce traffic; dense areas must remain load-test cases.

CHAPTER 14

Interest management and large worlds

Maintain a spatial index distinct from render visibility. Relevance includes distance, interaction potential, team/game rules, fast projectiles and doors/platforms that affect the player. A frustum alone is unsafe: objects behind the camera can collide with the player.

Collision residency and network visibility differ. The server loads enough collision cells for motion and interaction, including velocity-dependent margins and projectiles. A client prediction region includes static collision and required proxies beyond visible objects. Apply hysteresis to prevent churn near cell boundaries.

One room owner controls a physics island. Do not simulate the same dynamic contact pair independently on two shards. Begin with bounded scenes and portals; introduce ownership transfer only with freeze/transfer/resume semantics, state revision and proof that no input is applied twice.

For planetary-scale worlds, keep a high-precision global coordinate layer and local physics frames. Use region ID plus local coordinates; schedule origin changes consistently. Plan seam collisions and cross-region projectiles explicitly. Rapier in a bounded local frame is not proof that an entire planet can share one physics world.

CHAPTER 15

State restoration and determinism proof

Separate gameplay snapshots, network snapshots and engine checkpoints. They serve different purposes. A compact network snapshot is not necessarily sufficient to restore a contact-heavy physics world exactly; engine checkpoints may include contact caches and other internal state and require strict version compatibility.

Create a replay corpus of seeded inputs and versioned collision scenes. Run native and browser WASM builds from identical initial state. Compare canonical per-tick gameplay state and selected physics values; where exact parity is claimed require exact equality, with a separately reported tolerance mode only for diagnostic evaluation.

Test stacks, friction, slopes, jumping, moving platforms, joints, CCD, spawn/despawn ordering, origin changes and quantized inputs. Test the same full world before testing partial prediction worlds. A failure blocks deterministic-parity claims. Ordinary reconciliation tests additionally measure correction distributions under network delay.

Rollback interacting objects needs a consistent island checkpoint and replay of all affecting events. Do not restore one crate’s position while leaving its contacts, neighboring bodies and pending impulses at a different tick. If that cost is excessive, prefer server authority and interpolation for those objects.

CHAPTER 16

Security and trust boundaries

Clients request actions; they do not submit trusted outcomes. Validate authentication, room membership, action permissions, reach, movement limits and asset revisions. Validate finite numbers and message length before expensive parsing or physics work.

Protect against duplicate/out-of-order inputs, future tick abuse, input flooding, unauthorized world edits, oversized collision assets and spawn spam. Use rate limits per account, connection and room plus admission limits. TLS protects transit; it does not make a client trustworthy.

Admin interfaces require separate authorization. Secrets stay outside images and browser bundles. Record compact audit events for important decisions without logging credentials or unrestricted personal chat. Define retention and deletion policies before persistence launches.

Rust workspace and deployment

crates/replay-tools   parity and performance harness
web/                 renderer, UI, animation, documentation
infra/               Docker, local compose, deployment examples

Use async I/O for network tasks and dedicated bounded simulation workers for ticks. Each room serializes its own mutations. Share immutable asset geometry safely; avoid a global lock around all rooms. Profile allocation and copying before introducing unsafe code or exotic scheduling.

Build a multi-stage container with locked dependencies and a minimal non-root runtime. Declare supported CPU architectures. Configure resource limits, readiness/liveness endpoints, graceful room draining and termination deadlines. A container improves repeatable deployment; it neither guarantees speed nor removes host/kernel scheduling effects.

Sites hosts this documentation, not the native Rust simulation. Deploy the game server to infrastructure that can run native containers and the chosen persistent transport. Start with a single host or modest managed container deployment. Add orchestration only when recovery and scaling requirements justify it.

Operations and measurable budgets

MetricProposed initial acceptance / measurement

MemoryTrack idle, steady-state and peak load RSS; no sustained growth in a two-hour soak after warm-up.

BandwidthMeasure bytes/client/s, full baselines, dense-area peaks and outbound backlog.
PhysicsTrack active/sleeping bodies, collider count, contacts, CCD workload and solver duration.
RecoveryKill process mid-session; clients get explicit failure/rejoin flow. Persistent recovery meets agreed RPO/RTO.
CapacitySweep players and dynamic bodies independently; publish safe load envelope, never a single unsupported CCU number.

All numbers above are proposed gates, not achieved results. A 32-player room with 200 active dynamic bodies and streamed static collision is a useful first benchmark scenario, not a promised production limit. Add worst cases: pileups, players spawning together, simultaneous doors, reconnect bursts and asset loading.

Dashboards correlate tick time with scene complexity and queues. Trace network and asset work without flooding per-tick logs. Distinguish liveness from readiness: a running process may be unable to admit more rooms. Drain rooms before upgrades; incompatible simulation builds never join the same live session.

WebSockets conceal packet loss through retransmission; test resulting stalls rather than assuming application-level loss behaves like UDP. For a datagram transport, test actual loss and reordering semantics too. Simulated latency controls must be labeled as experiments.

Keep performance regressions in CI on stable benchmark runners, with artifacts identifying commit, simulation ID and scene. Screenshots alone cannot validate physics, security or scalability. Document known limits before a production release.

CHAPTER 20

Implementation sequence

  1. Decision spike: native/WASM Rapier parity, shared controller and collider cooking experiment; compare Jolt only if workload or parity results warrant it.
  2. Physics playground: inspect render-versus-collider overlays, shape counts, doorway sweeps, primitive/mesh cost and memory measurements.
  3. Network slice: authenticate room joins, fixed tick, input sequences, baselines and prediction/reconciliation.
  4. Shared interaction: server-owned crate and moving platform; document correction behavior and animation timeline.
  5. Content streaming: asset hashes, cell residency, activation ticks and safe procedural-building edits.
  6. Production hardening: bounded queues, quotas, fuzzing, load/soak tests, container deployment and recovery.
  7. Expansion: vehicles, complex interactions, optional transport upgrade and multi-region rooms after evidence.

Each phase updates this documentation with implemented behavior, measurements and unresolved risks. No “complete” label until its acceptance evidence exists.
